# Is the Hayali documentation agent-readable?

Research for #161 (map #159). Question: can an agent author a Hayali lesson in the single-file format (#125) from the published docs?

Method: read `apps/docs/content/en/hayali/**`, `apps/docs/nuxt.config.ts`, `content.config.ts`, `packages/hayali/docs/typedoc.json` and `src/typedoc-entry.ts`, the installed `@nuxt/content@3.14.0` module source, and the local prerender in `apps/docs/.output/public`. Live `https://karagoz.dev/*` could not be fetched from the sandbox (network approval pending), so claims about the deployed site are inferred from config and the local build, not observed.

## 1. Does the handbook cover the single-file format? No, not at all.

The handbook (`apps/docs/content/en/hayali/3.handbook/`, 0 to 8) describes only the `Lesson` TS/JSON object. A grep for `krgz-`, `parseLesson`, `from=`, `src=`, `carry`, `single-file` finds nothing in the handbook or the Hayali landing/setup/getting-started pages. #125 itself lists the format's handbook page as a follow-up ("written as a follow-up once the parser exists"); the parser has shipped (`packages/hayali/src/parse/`) but the page has not.

Gap list against the #125 format:

| Topic | In handbook? | Where it lives instead |
| --- | --- | --- |
| Overall structure: one `.md` per lesson, `# Title {#id}` chapter, `## Title {#id}` step, required ids matching `[A-Za-z0-9_-]+`, H3+ inside bodies | No (only "IDs are never derived from titles" in `1.lesson-schema.md`) | #125; ADR `packages/hayali/docs/adr/0003-lessons-as-plain-markdown.md`; `CONTEXT.md` glossary |
| Preamble / base tree (file fences before first H1) | No | #125 |
| `file=<path>` fences (base vs adjustment, position in step, plain fences stay body) | No | #125 |
| `from=<ref>` reuse (`chapter/step`, bare `step`, `base`; target must hold own adjustment; chains) | No | #125 |
| `src=` sibling-file fences and `resolveSrc` | No | #125 |
| `carry: <ref>` (one target, no `base`, own fences win, removals not carried, `carry-drops-removals`) | No. Handbook says "Steps are not cumulative" (`2.adjustments-and-removals.md`), which is still true for the compiled `Lesson` but now misleading for authors, since `carry` gives cumulative authoring | #125 |
| `krgz-lesson` keys (only `immutable`) | Partly: `immutable` is covered, as `Lesson.immutable` | #125 |
| `krgz-step` keys (`removals`, `locks`, `editor`, `preview`, `carry`); at most once; unknown keys are errors; other `krgz-*` names are errors | Per-key semantics are covered as schema fields (`3.locks`, `4.editor-directives`, `2.adjustments-and-removals`), not as YAML | #125 |
| Line specs: string shorthand `1-7, 13-17` (1-based inclusive) | No. Handbook documents only `3`, `[3, 7]`, `[2, [5, 7], 9]` | #125 |
| Editor / preview directives in YAML form | Semantics yes (open/close/highlight/preview.url, no inheritance, `line`), YAML syntax no | #125 |
| `parseLesson` API: `issues`, severity, `locate()`, `srcPaths`, never throws, run `validateLesson` too | No | #125; source `src/parse/` |
| Parse rule catalogue (`ref-cycle`, `unresolved-src`, ...) | No | #125 table; `src/parse/types.ts` |
| Callouts in bodies | Yes (`5.callouts.md`) | |
| Validation (`validateLesson`, `LessonIssue`) | Yes (`1.lesson-schema.md`, API reference) | |
| Worked example | No in docs; the docs demo is shown via `:hayali-demo` as a TS lesson | `packages/hayali/src/assets/demo-lesson.md` (in repo), `apps/docs/tests/hayali/demo-lesson.md` (test fixture) |

API reference: generated by typedoc from `src/typedoc-entry.ts`, which exports only the callout helpers, `i18nMessages`, `FullLayoutFrom`, the schema types and `validateLesson`/`LessonIssue*`. It does not export `parseLesson`, `ParseIssue`, `ParseIssueRule`, `ParseLessonOptions` or `ParseLessonResult`, so the `@karagoz/hayali/parse` subpath is absent from the reference too. The Hayali landing/setup pages do not mention the subpath either.

Locales: `content/{de,ar}/hayali/3.handbook/` mirror the English pages, so any new page also needs de/ar counterparts (or an explicit "English only" decision), otherwise those routes 404 or fall back.

## 2. Can an agent fetch clean Markdown from karagoz.dev?

Not today; only rendered HTML.

- `nuxt.config.ts` modules are `@nuxt/content`, `@nuxtjs/i18n`, `@nuxthub/core`. `nuxt-llms` is not installed.
- In `@nuxt/content@3.14.0`, `dist/module.mjs` installs the `features/llms` module only `if (hasNuxtModule("nuxt-llms"))`. That feature is what registers `/raw/**:slug.md` (`addServerHandler({ route: "/raw/**:slug.md" ... })`) and the `llms.txt` / `llms-full.txt` generation plugin. Without `nuxt-llms` neither exists.
- The local prerender (`apps/docs/.output/public`) confirms it: no `llms.txt`, no `*.md` files, no `/raw`. Public files are `*.html` per route (e.g. `hayali/handbook/adjustments-and-removals.html`), `_payload.json` per route, `_nuxt/`, and `dump.content_{en,de,ar}.sql`.
- The prerendered HTML (`ssr: true`, `crawlLinks: true`) contains the full page text, so an agent can read it as HTML. It carries nav/layout chrome and the Shiki-highlighted code as spans; a text-extracting fetcher copes, but code fences lose their language tag and exact whitespace is at the mercy of the fetcher.
- `dump.content_en.sql` is gzip+base64 of the content AST (minimark), served as a static asset. Not usable as Markdown.
- `content.config.ts` collections use `type: 'page'` with no `rawbody` column in the schema, so the Content query API (`/__nuxt_content/content_en/query`, POST) returns AST, not source Markdown. (Not verified against a running instance.)
- The canonical Markdown source is public in the GitHub repo: `https://raw.githubusercontent.com/frontendat/karagoz/main/apps/docs/content/en/hayali/3.handbook/<n>.<slug>.md`. Caveats: the numeric prefix is part of the filename but not the site URL (`/hayali/handbook/locks` is `3.locks.md`); MDC components (`::hint`, `:hayali-demo`) appear raw; the API reference is generated into `content/en/hayali/4.api-reference/` and checked in (the `validateLesson.md` page includes a `Defined in` GitHub link, so the generated files are in the repo).

Options to make the site itself agent-readable, cheapest first:
1. Add `nuxt-llms` (the module Nuxt Content integrates with). It gives `/llms.txt`, `/llms-full.txt` and `/raw/<path>.md` per page, per collection. Needs a decision for the three locale collections and for the Cloudflare prerender (`/raw/**` and `/llms*.txt` must be in `nitro.prerender.routes`; `crawlLinks` will not discover them).
2. Hand-written `public/llms.txt` listing the raw GitHub URLs. No dependency; drifts by hand, and still points at GitHub.
3. Point the skill at the GitHub raw URLs only (no docs-site work).

## 3. Anything else on the site the skill should link to?

- API reference: `/hayali/api-reference/{interfaces,type-aliases,functions,components,variables}/<Name>` for `Lesson`, `Chapter`, `Step`, `AdjustmentsTree`, `EditorDirective`, `LineSpec`, `Position`, `PathPattern`, `LessonIssue`, `LessonIssueRule`, `validateLesson`. Useful for schema field names; has no parser pages (see section 1).
- Demo lesson: shown interactively via `:hayali-demo` on the Hayali landing and getting-started pages (TS lesson, not Markdown). The Markdown source is only in the repo: `packages/hayali/src/assets/demo-lesson.md` (also the fixture `apps/docs/tests/hayali/demo-lesson.md`).
- Not on the site at all: `packages/hayali/CONTEXT.md` (vocabulary), ADR 0003, #125 (the only complete format spec today).

## Recommendation

Answer to #161:

1. The handbook does not cover the single-file format. The skill cannot "point at the handbook instead of copying the spec" (map #159 note) until a handbook page for it exists. Make writing that page (structure, `file=`/`from=`/`src=`, `carry`, `krgz-lesson`/`krgz-step` keys, line-spec shorthand, ids, `parseLesson` + issue rules, worked example from `demo-lesson.md`, plus de/ar counterparts or an explicit English-only call) a prerequisite ticket of the skill spec, together with exporting `parseLesson` and its types from `typedoc-entry.ts` so the API reference documents `@karagoz/hayali/parse`. Also amend `2.adjustments-and-removals.md` ("Steps are not cumulative") to say this is about the compiled `Lesson` and that `carry`/`from=` give cumulative authoring.
2. URL form the skill should point at: the human URL `https://karagoz.dev/hayali/handbook/<slug>` works today as prerendered HTML (readable, but chrome and no code languages). For clean Markdown, today only `https://raw.githubusercontent.com/frontendat/karagoz/main/apps/docs/content/en/hayali/3.handbook/<n>.<slug>.md` works. Preferred end state: install `nuxt-llms` so `https://karagoz.dev/raw/en/hayali/handbook/<slug>.md` and `/llms.txt` exist, then point the skill at `/llms.txt` as the entry. Until then, the skill should name the handbook index and the raw GitHub form, and carry the worked example in its own folder (already planned), since the repo-only `demo-lesson.md` is not reachable from a reused-elsewhere skill.
3. Because the skill folder is to be reused in another project, it cannot rely on repo paths; the bundled worked example plus a link to the handbook page (once it exists) is the minimum self-contained set. #125 is a GitHub issue, not a stable doc, so do not link it from the skill.
