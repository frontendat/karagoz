# Lesson Files

A [lesson](/hayali/handbook/lesson-schema) does not have to be written as an object. It can be one Markdown file, a
**lesson file**, that [`parseLesson()`](/hayali/api-reference/functions/parseLesson) compiles to the same `Lesson`. You
write prose and code in real fences, and read the lesson from top to bottom.

`parseLesson()` comes from `@karagoz/hayali/parse`. It is pure and has no Vue or Node dependency, so it runs in the
browser, in a build script or in a test. It never throws: whatever could be built is returned together with a list of
issues.

```typescript
import { parseLesson } from '@karagoz/hayali/parse'

const { lesson, issues } = parseLesson(markdown)
```

A lesson file is written in one language. A translation is a separate file with the same ids.

## The shape of a file

````markdown
```yaml krgz-lesson
immutable:
  - package.json
```

```json file=package.json
{ "name": "tiny-counter", "private": true }
```

```html file=index.html
<button id="button">Click me</button>
```

```js file=app.js
// Behaviour goes here.
```

# The page {#basics}

## Markup {#markup}

Every page starts as HTML. `index.html` is open in the editor.

```yaml krgz-step
editor:
  open: [index.html]
```

## Behaviour {#behaviour}

`app.js` now handles the click.

```js file=app.js
document.getElementById('button').addEventListener('click', () => alert('Hi'))
```

```yaml krgz-step
editor:
  open: [app.js]
```
````

| Markdown | Becomes |
| -------- | ------- |
| `# Title {#id}` | A chapter. |
| `## Title {#id}` | A step of the current chapter. |
| Text under a step heading | The step's `body`. |
| A fence with `file=<path>` | A file: in the base tree before the first chapter, an adjustment inside a step. |
| A `krgz-lesson` fence | Lesson-wide settings, before the first chapter. |
| A `krgz-step` fence | The step's directives, inside the step. |

Only `#` and `##` headings structure the lesson. Deeper headings are part of a step's body.

## Ids

Every chapter and step heading ends with an `{#id}`. An id uses letters, digits, `_` and `-`. Chapter ids are unique in
the lesson, step ids within their chapter. As in the [lesson schema](/hayali/handbook/lesson-schema), ids are never
derived from titles. A heading without an id, or with an invalid or repeated one, is an error. A chapter without steps
is an error too.

## Lesson block

The optional `krgz-lesson` fence holds lesson-wide settings. Today it has one key, `immutable`, a list of
[immutable file](/hayali/handbook/adjustments-and-removals) patterns. At most one lesson block is allowed, and only
before the first chapter heading.

````markdown
```yaml krgz-lesson
immutable:
  - package.json
  - server.js
```
````

## File fences

A fence whose info string has `file=<path>` is a file. Before the first chapter it belongs to the **base tree**; inside
a step it is one of the step's [adjustments](/hayali/handbook/adjustments-and-removals). A path can appear once per
step, and once in the base. A fence takes its content from **one** of three places:

| Written as | Content comes from |
| ---------- | ------------------ |
| A body | The fence itself. |
| `from=<ref>` and an empty body | Another step's version of the same file. |
| `src=<path>` and an empty body | A file next to the lesson file. |

Giving a fence a body together with `from=` or `src=`, or giving it both `from=` and `src=`, is an error.

### from=

`from=` reuses a file instead of copying it, which is how a step keeps what an earlier step wrote:

````markdown
```css file=style.css from=style
```

```js file=app.js from=basics/behaviour
```
````

A reference is a step id in the same chapter (`style`), a step in any chapter (`basics/behaviour`), or `base` for the
base tree's version. The step must have its own version of that file, or get one through its `carry`; the base is not
consulted unless you ask for it. The parser expands references, so the compiled `Lesson` contains none.

### src=

`src=` loads the content from another file, for code that is too long to read inline. The path is relative to the
lesson file and must stay inside its folder. Parsing is pure, so you supply the reader through the `resolveSrc`
option; without it, every `src=` is unresolved. `srcPaths` in the result lists what was requested, which is what a
bundler needs to invalidate its cache.

```typescript
const { lesson } = parseLesson(markdown, {
  resolveSrc: (path) => files[path],
})
```

## Step block

The optional `krgz-step` fence holds one step's directives. At most one is allowed per step.

````markdown
```yaml krgz-step
locks: [index.html]
removals: [about.html]
editor:
  close: [style.css]
  open:
    - path: app.js
      line: 6
  highlight:
    - path: style.css
      lines: 1-7, 13-17
preview:
  url: /about.html
```
````

| Key | Same as | See |
| --- | ------- | --- |
| `locks` | `Step.locks` | [Locks](/hayali/handbook/locks) |
| `removals` | `Step.removals` | [Adjustments and Removals](/hayali/handbook/adjustments-and-removals) |
| `editor` | `Step.editor` | [Editor Directives](/hayali/handbook/editor-directives) |
| `preview` | `Step.preview` | [Editor Directives](/hayali/handbook/editor-directives) |
| `carry` | | [Carry](#carry) below |

Unknown keys are errors, so typos do not pass silently. So are fences named `krgz-` something else.

### Line specs

In `editor.highlight`, `lines` accepts the [line spec](/hayali/api-reference/type-aliases/LineSpec) as YAML (`7`,
`[3, 7]`, `[[1, 7], [13, 17]]`) or as shorthand text: `7`, `3-7`, `1-7, 13-17`. Lines are 1-based and inclusive.

## Carry

Steps are not cumulative: each starts from the base and only its own adjustments. `carry` opts in to starting from
another step instead:

````markdown
## Behaviour {#behaviour}

```yaml krgz-step
carry: style
```

```js file=app.js
// Only the new file is written. style.css comes from the "style" step.
```
````

The step gets every file of the step it carries, plus its own fences, which win when both name the same path. The
reference is a step id (same chapter) or `chapter/step`. A carried step can carry another, and the chain is followed.

Only **adjustments** are carried. Locks, editor directives, the preview and removals are never inherited, because
they describe one step's moment, not its files. If the carried step removes a file that this step carries back in, you
get a warning.

## Issues

`parseLesson()` returns a [`ParseIssue`](/hayali/api-reference/interfaces/ParseIssue) for every problem, each with a
1-based `line`, a `severity` of `error` or `warning`, and a
[`rule`](/hayali/api-reference/type-aliases/ParseIssueRule) naming what went wrong:

| Area | Rules |
| ---- | ----- |
| Headings and ids | `missing-id`, `invalid-id`, `duplicate-id`, `step-outside-chapter`, `empty-chapter` |
| Fences | `unclosed-fence`, `unknown-fence`, `file-outside-step`, `missing-file-path`, `duplicate-file` |
| Blocks | `malformed-yaml`, `unknown-key`, `invalid-value`, `misplaced-lesson-block`, `duplicate-lesson-block`, `misplaced-step-block`, `duplicate-step-block` |
| File sources | `conflicting-file-source`, `ref-with-body`, `src-with-body`, `invalid-src`, `unresolved-src` |
| References | `ref-unknown-step`, `ref-missing-path`, `ref-cycle` |
| Carry | `carry-unknown-step`, `carry-cycle`, `carry-drops-removals` (the only warning) |
| Other | `parser-failure` |

Errors inside a `krgz-lesson` or `krgz-step` block point at the exact key. The `lesson` in the result is best-effort,
so it is still there when there are errors; fix them before relying on it.

### Parsing and validation

Parsing checks the file's syntax. [`validateLesson()`](/hayali/api-reference/functions/validateLesson) checks the
compiled lesson against each step's resolved files, for example a highlight on a file the step does not have or on a
line past its end. They report different problems, so run both. Validation issues name a chapter, step and path, not a line; use `locate()` from the result to
put them back on one.

```typescript
import { parseLesson, validateLesson } from '@karagoz/hayali/parse'

const { lesson, issues, locate } = parseLesson(markdown)
for (const issue of issues) console.log(`${issue.line}: ${issue.rule} ${issue.message}`)

if (!issues.some((issue) => issue.severity === 'error')) {
  for (const issue of validateLesson(lesson)) {
    const line = locate({ chapterId: issue.chapterId, stepId: issue.stepId, path: issue.path }) ?? 1
    console.log(`${line}: ${issue.rule} ${issue.message}`)
  }
}
```
