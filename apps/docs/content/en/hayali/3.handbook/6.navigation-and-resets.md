# Navigation and Resets

The learner moves between steps with the Prev/Next buttons, the table of contents dropdown in the toolbar, or by
clicking a step in the step list. The step list shows the steps of the current chapter; chapters are reached through
the table of contents.

## The position

The current step is the `position` model, a [`Position`](/hayali/api-reference/interfaces/Position) of
`{ chapterId, stepId }`. Bind it with `v-model:position` to read it, restore a saved position or deep-link to a step.
If you leave it out, the lesson starts at the first step of the first chapter. Hayali never stores the position itself.

Step IDs are only unique within a chapter, so a position is the `chapterId` and `stepId` together. Hayali does no
routing: bind the model to whatever your framework offers, such as a query parameter, a hash or a path segment.

If the bound position names a step that doesn't exist, for example a stale link, Hayali shows the first step, writes
that position back to the model so your binding corrects itself, and logs a warning in development.

## Deep links

Bind the position to your router to make steps linkable. This site's demo keeps it in a query parameter,
`?step=chapterID/stepID`:

```ts
const route = useRoute()
const router = useRouter()

// Start at the first step, so hydration matches the HTML, then apply the URL once mounted.
const position = ref({ chapterId: 'basics', stepId: 'markup' })
onMounted(() => {
  const linked = parseStep(route.query.step)
  if (linked) position.value = linked
})

// Write changes back with `replace`.
watch(position, ({ chapterId, stepId }) => {
  void router.replace({ query: { ...route.query, step: `${chapterId}/${stepId}` } })
})
```

* **Query over hash.** A query is part of the request and survives path changes. A hash never reaches the server.
* **Apply it after mount.** Prerendered pages are served without the query, so the first render has to be the start
  step. Setting the position during setup would not match that HTML, and hydration would leave the toolbar and the
  sandbox out of step. Setting it in `onMounted` is early enough: the sandbox boots with the linked step's files.
* **Language prefixes don't matter.** A query is independent of the path, so it works the same under `/de/` and
  `/ar/`.
* **Replace, don't push.** Setting the model from outside skips the [confirm dialog](#resets-and-the-confirm-dialog)
  and the reset, so a Back button that changed the position would leave the files out of step. Read the URL on load
  only.
* **Bad links are safe.** A link to a step that no longer exists shows the first step and corrects the model, so
  your URL heals itself.

## Resets and the confirm dialog

Every step starts from a known state. When the learner moves on, the resettable files are restored to the target
step's tree (see [adjustments and removals](/hayali/handbook/adjustments-and-removals)). A file counts as **dirty** once
the learner has edited it. While files are dirty, moving to another step first asks for confirmation, because their
changes will be lost.

* **Continue** resets the files and moves.
* **Cancel** changes nothing: not the position, the files, the open tabs or the preview.

::hint
Only resettable files are tracked. Edits to [immutable files](/hayali/handbook/adjustments-and-removals) never make the
lesson dirty and are never reset.
::

## One move at a time

Navigation is single-flight. From the confirm dialog until the new step is in place, the toolbar and the step list are
disabled and further navigation requests are ignored; they are not queued. Editor and preview directives are applied
afterwards, in the background, and a newer step always cancels the unfinished directives of an older one.

## On entering a step

After the reset, Hayali applies the step's [editor directives](/hayali/handbook/editor-directives) in a fixed order:
clear old highlights, close and open tabs, highlight, go to a line, then the preview.
